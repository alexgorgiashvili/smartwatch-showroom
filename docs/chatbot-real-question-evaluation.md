# Website chatbot: customer-question evaluation (2026-09-26)

## Scope and privacy

- Read-only local conversation inventory: 122 customer text messages from the website widget, 20 Facebook, 15 Instagram, and 2 WhatsApp. The website messages include 22 question-like price messages, 8 SIM/network, 7 delivery, and smaller stock, payment, warranty, calling, GPS, and water-resistance groups. These counts overlap when one message has multiple topics.
- Evaluated 17 short, manually reviewed **paraphrases of observed customer question types**, never raw transcripts or personal details. These are representative questions, not verbatim customer quotations or an independent random sample. The previous 120 frozen scenarios are synthetic and were not used as evidence of live correctness here.
- Requests went through the local Laravel /chatbot route and the real gpt-6-luna API. All writes were to an isolated in-memory SQLite database. No production chatbot request, database write, migration, or deploy was performed.
- The 17 questions covered delivery fee/time, cash payment, warranty, model exchange, SIM, video calling, price, stock, installments, refund, waterproofing, battery, GPS, network compatibility, same-day regional delivery, and setup app. The catalog was intentionally empty for these cases, so hardware claims required a clarification.
- Four further route-level questions used two **fictional SQLite products** with different prices and stock states. They test product-specific evidence handling; they do not verify current production inventory.

## Findings and changes

| Finding | Before | Change | Recheck |

The first 17 route responses included three actionable quality issues above. Policy answers for delivery, cash payment, 4G warranty and conditional exchange matched the verified site terms. No unsupported numeric price or stock promise was observed with an empty catalog. Focused Luna rechecks passed after fixes. This is a small targeted review, not a measured overall accuracy rate.

## Checks

- Targeted SQLite automated suite: 31 tests, 93 assertions passed, including route-level wrong-price/stock rejection and valid out-of-stock response.
- Real Luna rechecks used the same local /chatbot route. The final setup answer requested a model name or product link and did not promise an unverified app name.
- Paid requests stayed well below the previously authorized $3 ceiling by limiting the number of cases and disabling the auxiliary intent model in the evaluation. Exact token-based aggregate spend for this manual run was not captured, so no cost metric is claimed.

## Remaining limits

- Current production catalog contents and physical stock were not copied into the test database. Product-specific production answers still need a read-only catalog review and a follow-up isolated test with those public fields.
- Historical Messenger data informed the earlier topic audit, but this run selected questions from local channel records only. Instagram history remains inaccessible through the configured API.
- The owner approved deployment after the isolated evaluation. Commit `14cd6b0` was fast-forwarded to production on 2026-09-26 without a migration, cache clear, or changes to existing unrelated server files. Production configuration still selects `gpt-6-luna` for 100% of widget conversations and `gpt-4.1-mini` for social channels.
- A single clearly marked test question sent through the public live `/chatbot` endpoint returned HTTP 200. The answer withheld a refund promise and explained the conditional 14-day model exchange. This smoke test created an ordinary production chat record and admin notification; it is not a full production quality sample.
- Public home and catalog pages returned HTTP 200. A read-only production runtime check loaded the refund policy, rejected a cross-product false price and stock claim, and accepted the correct out-of-stock claim.

## Expanded question sweep and corrections (2026-09-26)

The follow-up used all 20 risk-focused policy questions and all 120 controlled, synthetic questions built from observed customer topic frequencies. These are not verbatim customer messages. Requests used the local `/chatbot` route, real `gpt-6-luna`, the enabled auxiliary intent model, and an isolated in-memory SQLite database. The test catalog contained no products. Private answers and the API cost ledger stayed in ignored local test storage; this report includes only aggregates.

The first policy run revealed missing regional delivery estimates, an incorrect refusal to describe online card payment, a false stock-validator hit on payment availability, and unclear wording about exchanging a used item. The widget knowledge and stock validator were corrected. A second run of all 20 policy questions returned HTTP 200 with no fallback or validation violation. Manual review found the published delivery estimates, online card and Tbilisi-only cash payment, 2G/4G warranty periods, conditional 14-day model exchange, and the absence of a verified cash-refund promise correctly represented. This is manual review of a small controlled set, not an independent accuracy percentage.

The first 120-question topic sweep had 37 intent-label mismatches and six published answers containing Armenian characters or punctuation. A GPS mention had been treated as a recommendation even in price, stock, comparison, and feature questions. The widget now reserves that shortcut for actual recommendation wording while leaving the social-channel heuristic unchanged. The widget also normalizes two Armenian punctuation marks, rejects remaining Armenian script, and uses a relevant safe reply for an empty-catalog price question. The synthetic generator and 120-case file were corrected for Georgian case endings.

On the second full sweep, all 120 requests returned HTTP 200. The intent-label mismatch count fell to 15. No published answer contained Armenian script, a numeric product price, or an affirmative stock claim with the empty catalog. Three answers used the locale safety fallback. Median route latency was 3,295 ms and p95 was 3,880 ms, compared with 2,999 ms and 3,834 ms on the first sweep. The 46 ms p95 difference is small and is not evidence of a production latency improvement. Full metered API cost for the second sweep, including helper model calls, was $0.08594581, compared with $0.09274757 on the first sweep. Those are costs per attempted answer; no independent success grade exists for a cost-per-success figure.

Ten questions with a final wording correction were rerun within a 14-case targeted subset: all returned HTTP 200, one used a price-specific locale fallback, no published answer contained Armenian script, and one case's intent label differed from the synthetic expectation. The cost of this subset was $0.00440717. The full local ledger for these follow-up paid runs is $0.21477836. The earlier model-only benchmark recorded $0.0367452. A prior 17-question manual run did not capture exact aggregate usage, so a single exact historical spend total cannot be claimed; the new runs enforced an additional $2.50 cap with per-request reserve against the authorized $3 ceiling.

The remaining 15 intent-label mismatches in the full sweep often still produced useful answers (for example, a delivery answer despite a stock intent). They were not automatically counted as factual errors. Some safe refusals ask for a model even though a product category was supplied, because SQLite had no catalog; the current production catalog must be tested separately before broad product-specific answer quality can be claimed. Test contact links came from SQLite defaults and do not establish production contact settings.

Commit `69192d4` was fast-forwarded to production without a migration or cache clear. Existing unrelated server changes were preserved. A read-only runtime check showed `gpt-6-luna` at 100% for the website widget and `gpt-4.1-mini` for social responses. Two clearly marked synthetic live `/chatbot` questions returned HTTP 200 without fallback. The regional-delivery reply gave the verified 1–3 working-day estimate with a caveat. The Wonlex CT23 reply gave the current sale price of 149 GEL, compared with the regular 179 GEL, and said it was in stock; a read-only production catalog check showed sale price 149 GEL and three available units. These two live requests created ordinary chat records and admin notifications. They are smoke checks, not a production accuracy sample.

## Real customer wording replay (2026-09-27, local changes only)

The earlier frozen 120 scenarios were synthetic. This separate set contains **120 actual customer question wordings** selected from existing records: 58 website-widget, 1 WhatsApp, and 61 Messenger. The questions were de-identified and each was replayed as a new conversation through the local `/chatbot` route with `gpt-6-luna` and the normal auxiliary intent model. The route used an isolated in-memory SQLite database seeded with a read-only snapshot of public catalog fields (12 active products, 35 variants). Catalog prices and stock in that snapshot are test evidence for this run, not a guarantee of present physical stock. Private questions, answers, catalog fixture, and usage ledger remain in ignored local test storage; none is committed here. This was evaluation and application-level correction, **not model-weight training or fine-tuning**.

Read-only Messenger collection found 416 conversations. The later complete message audit saw 4,909 message records; 221 records in the question extraction pass contained no text. Instagram history was unavailable through the configured read path. Thus the 120 cases provide broader coverage than the local widget database, but are neither a random sample nor a complete multi-channel history. Some questions refer to an earlier message or product; a fresh-conversation replay cannot independently grade the expected answer to those cases.

The first full replay uncovered false catalog-empty answers for broad price/recommendation questions, missing live catalog evidence for video calls, SIM, water resistance and colors, an arbitrary model selected for a context-dependent follow-up, incomplete delivery-plus-contact replies, and a misleading implication that a six-product shortlist was the whole catalog's price range. Local widget-only changes now use public catalog fields for broad questions, supply relevant feature evidence, ask for a model or budget when prior context is absent, answer both parts of combined questions, and describe shortlist prices as examples. A helper-model string value of `"null"` is normalized to an absent product entity for the widget. Targeted replays confirmed the corrections for the observed examples, including a text-only photo request. Social-channel prompts and model selection were not changed.

The latest **full** 120-case replay returned HTTP 200 for all cases. Its median latency was **3,133 ms**, p95 was **4,214 ms**, and metered API cost (including helper calls) was **$0.10500948**, or about $0.000875 per attempted answer. It produced two strict-Georgian fallbacks and one validator fallback. The sole heuristic catalog-denial flag concerned an accessory absent from the watch catalog, so it was not a false denial of an available watch. The fallback review found an unhelpful answer to the cheapest-watch question and an overly generic response to a complaint about an unverified advertised price. Their targeted replays now return a catalog-grounded cheapest-watch answer and a cautious request for the ad link/model, respectively. A price-only comparison with an unnamed watch and a broad budget question also passed targeted rechecks. These final small corrections have **not** had another full 120-case replay.

An earlier cleaned run contained 118 valid customer questions (two automated call notices were excluded afterward), with metered cost about $0.097072. The 118- and 120-case sets are not identical and were run at different times; neither proves a latency or cost improvement. The latest full run's p95 and cost per attempted answer were numerically higher. A prior 120-case run had p95 4,423 ms and cost $0.04925478, showing substantial run-to-run cost variation. The cumulative metered local ledger for this work is about **$0.857**, below the authorized $3 ceiling.

On the **118 shared case IDs**, a paired read of the saved outputs found aggregate metered cost rising from **$0.09707192 to $0.10315995** (+6.3%) and nearest-rank p95 latency rising from **3,800 to 4,503 ms**. The model-call count was almost unchanged (206 to 207). API timing and output length vary between runs, so these numbers locate a release risk rather than isolate a single cause. They do not satisfy the planned 20% cost-per-success reduction or the non-worsening p95 gate.

No independent, context-aware pass/fail grading exists for all 120 answers. Heuristic flags and selected manual reviews identified defects but cannot establish a five-point quality uplift or a cost **per successful answer**. The measured p95 is also worse than the earlier local run. The original release gates therefore remain **unproven or unmet**; this branch has not been deployed. Production still runs its previously deployed `gpt-6-luna` widget configuration. Before deploying these local corrections, a reviewer needs to grade the frozen cases with their conversation context and verified catalog/policy evidence, then repeat a comparable latency and cost-per-success evaluation. The existing widget cohort configuration supports staged activation and rollback once those gates are met.

Privacy correction: Two Messenger automated call notices that contained personal names were inadvertently included in the initial API replay. They were removed from the ignored derived files, the collector now excludes that notice pattern, two genuine customer questions replaced them, and the 120-case run was repeated. Local removal cannot erase an earlier provider request. [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data) state that API content is not used to train models by default without opt-in, while default abuse-monitoring logs can retain prompts and responses for up to 30 days, subject to stated exceptions; this account's retention setting was not verified. Future API replays of historical messages require manual input review before submission.

Focused automated checks on the local changes passed **39 tests and 111 assertions** using the temporary SQLite configuration. PHP syntax checks and `git diff --check` passed. No production DB write, migration, cache clear, or deploy was performed for this 2026-09-27 replay.

## Full real-question recheck after manual review (2026-09-27)

A manual read of the 120 de-identified local responses found several concrete failures: broad camera and water questions could be mistaken for an exact request for the first returned product; the camera field was omitted from the prompt; a Q12/Q21 comparison omitted a shared touchscreen feature; short follow-ups without earlier context picked an arbitrary model; and a two-model recommendation combined different prices into one discount claim. The widget-only code now identifies a requested product from the customer's own wording, includes relevant catalog fields and up to six feature candidates, keeps comparison functions visible, requests clarification on short context-dependent first turns, and instructs separate price attribution for each product. Social-channel response configuration was not changed.

The same frozen 120 actual customer wordings were then replayed through the local `/chatbot` route against the isolated SQLite catalog snapshot. **120/120 returned HTTP 200**; median latency was **2,759 ms**, p95 **3,476 ms**, total metered API cost **$0.09120553** including helper calls, and model calls totaled 193. There was one strict-Georgian fallback for an arithmetic question and one validator fallback for an unverified advertised price. The published fallback replies were cautious. A heuristic catalog-denial flag concerned an accessory absent from the watch catalog; its other flag was a deliberate zero-call clarification. Targeted replays confirmed that camera examples had catalog evidence, the Q12/Q21 comparison described shared functions correctly, and an ambiguous price/color follow-up asked for a model. Four grouped-price answers were manually checked against the snapshot and attributed prices correctly.

For the **118 case IDs shared** with the earlier cleaned baseline and latest prior full run, the new run cost **$0.08935845** and p95 was **3,497 ms**. The cleaned baseline was **$0.09707192** and **3,800 ms**; the latest prior run was **$0.10315995** and **4,503 ms**. Thus cost fell about **8% versus the baseline** and **13% versus the latest prior run**. p95 also improved in this local run. The cumulative metered ledger is approximately **$0.962**, under the $3 paid-evaluation ceiling. The focused SQLite suite passed **44 tests, 135 assertions**; PHP syntax and `git diff --check` passed. The complete 120-case route replay passed **129 assertions**.

These results do **not** establish the planned 20% lower cost per successful answer or a five-percentage-point quality improvement: the 120 answers still lack independent, context-aware success labels, and the paired *attempted-answer* cost reduction is below 20%. Some original customer questions depend on earlier conversation turns that this fresh-session replay does not contain. The catalog describes IP67 for several products, but one generated reply interpreted that code as splash protection and advised against swimming; that interpretation should be checked against approved product guidance before being treated as a store policy. The branch remains local and **is not ready for another production rollout** under the original acceptance criteria.
